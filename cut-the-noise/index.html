02Cut the Noise

The old software factories are in trouble. Work that used to take weeks or months is now a few keystrokes away. Our focus is shifting toward understanding the customer experience, balancing agent speed with production reliability, and building agentic systems we can trust.

03The old software factory

A human builder fills code boxes upstream while another reviews the changes. Writing code paced the old factory, leaving time to explain how the system worked and teach new teammates through review.

04The factory speeds up

With agents at the helm, writing code is no longer the bottleneck. Our assumptions about how work moves through the factory are breaking: code arrives faster, while the human reviewer’s capacity has not grown along with it.

05Review load

More PRs arrive at each active reviewer, and the changes themselves are larger. Our illustrative workload estimate combines those trends. This is why writing code faster creates a new bottleneck in the attention required to understand and review it.

06Cognitive surrender

The person at the end of the line has not gained the capacity to inspect the pile. When the output overwhelms our attention, we can disengage and approve without really understanding the change.

07A little about me

I’m Joah Gerstenberg, a tech lead at Block focused on risk-based agent autonomy. I spent the first decade of my career building web experiences, which shaped how I think about the purpose of our code.

08The code was never the goal

The intended experience is a customer buying one coffee for one dollar, charged once. The code is an implementation of that plan. Peter Naur’s idea of programming as theory building reminds us that our understanding of the customer, the reasons for our choices, and the intended experience lives in the minds of the builders. We have to carry that understanding into agent-written systems.

Source: Programming as Theory Building, 1985

09We are still responsible

The planned one-dollar coffee purchase becomes two charges. The panicking coffee shop owner points to the engineer, who points to the goose. The agent cannot take responsibility for the customer’s experience. We still have to understand what happened and make it right.

10Offline and online evals

Offline evaluations measure precision—the share of findings that are valid—and recall—the share of known defects found. Online evaluations measure address rate, whether engineers act on findings, and change fail rate, the share of merged changes later reverted or corrected in a follow-up commit. Use a consistent follow-up window and count each failed change once.

11Calibrate to past human reviews

Human experts inspect historical code changes and record valid findings and known defects. Those paired examples give us a reference for calibrating and evaluating the reviewer, so its judgments can be compared with past human reviews.

14A reviewer that’s muted catches nothing

A reviewer that raises flags on clean code loses engineers’ attention. A valuable finding can disappear among those false alarms. DoorDash and Figma both set a high bar for precision because a review stream that engineers ignore provides little protection.

Sources: DoorDash · Figma

17Specialist reviewers

Specialist reviewers ask different questions about the same change. Money movement, security, and correctness illustrate distinct perspectives. The comparison here is one general reviewer versus a team of three specialists. In an offline evaluation on 100 historical PRs using the same model, three specialists found 52% of known bugs compared with 41% for one reviewer. This gain is recall; the available partial diagnostics also showed lower precision, reinforcing the need to challenge and deduplicate their findings.

Block internal data

18Match review to risk

Don’t send every review to the full panel. Assess the change’s risk signals and reserve the most expensive reviews for the highest-risk changes. Routine work gets a smaller review; money movement or a security boundary brings in specialists and a different policy for human attention.

19Reviewers, coordinator, judge, human

Money movement, security, and correctness specialists send their findings to a coordinator that deduplicates overlap. A judge challenges the evidence and rejects weak findings before handing sensitive changes to the human. More perspectives broaden coverage, while validation layers improve precision.

Sources: DoorDash · Figma

20Reserve human attention

Reserve human review for the most sensitive changes: infrastructure, judgment-sensitive behavior, money movement, and personally identifying information. These signals should reflect the application. An agent’s silence does not remove the need for human judgment.

21What is my job now?

If agents write code and help review it, what is the software engineer’s job? The responsibility shifts toward understanding the experience, setting boundaries, and deciding where human judgment is still essential.

22Contain and Align

The human controls how much autonomy the agents get and provides the context they need. The risk lever bounds what happens on the production path; the shared notebook aligns the reviewers with the intended customer experience.

23Give your agents the big picture

Instructions, skills, and tools should convey why the system exists and what a successful customer experience looks like. The same context notebook carries the simple intent: one coffee purchase, charged once.

24Get review before the code is written

Humans and agents collaborate on the shared plan while it is still easy to change. Buzz represents that ongoing conversation around intent, before implementation becomes a pile of code to review.

Source: Buzz, buzz.xyz

25Cut the noise

Prioritize precision, calibrate against past human reviews, and measure performance in real work. Match review depth to risk and reserve human judgment for sensitive changes. Give agents the customer experience and intent behind the code, and get review while the plan is still easy to change.

26This is better

The factory keeps moving while agents review the code and humans discuss the customer experience over coffee. The goal is a calmer system that protects attention and keeps judgment where it matters.
