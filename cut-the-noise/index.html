Cut the Noise

Building a code reviewer you can trust

01Cut the Noise

Code is cheap now. The harder question is whether we can trust the review that follows it. This talk is about building a code reviewer that earns our attention and helps us deliver experiences we can stand behind.

02The old bottleneck

We used to inspect one change at a time. Writing code paced the factory, and human review could keep up with the changes arriving at the end of the line.

03The factory speeds up

Agents have removed many of the old bottlenecks. The code arrives faster, but the human reviewer’s capacity has not grown along with it. Our old assumptions about how work moves through the factory are breaking.

04More code, modest productivity gains

Code generation has increased dramatically, while productivity gains have been more modest. These illustrative graphs show direction, not measured time series or an exact ratio. The source uses different cohorts and baselines for the two comparisons.

05Review waits and code churn

More output can mean more time waiting for a first review and more code churn. Faros observed increases across periods of lower and higher AI adoption within organizations. These curves illustrate the trends rather than monthly measurements or a causal relationship.

06Cognitive surrender

The person at the end of the line has not gained the capacity to inspect the pile. When the output overwhelms our attention, we can disengage and approve without really understanding the change.

07We still own the experience

When a customer brings back a broken experience, pointing to the agent does not solve their problem. We are still responsible for what we deliver, and we have to be able to hold that responsibility.

08A little about me

I’m Joah Gerstenberg, a tech lead at Block focused on risk-based agent autonomy. I spent the first decade of my career building web experiences, which shaped how I think about the purpose of our code.

09The program is bigger than the code

The customer buying coffee is the point of all this machinery. The program includes our understanding of the problem, the intended experience, and the reasons behind our choices. That theory lives in its creators’ minds, and the code does not capture all of it.

10Calibrate against human judgment

Trust starts with evaluations. Past expert reviews give us examples of what good review looks like in our application. Preserve the judgments and their context, include clean changes and known failures, and use that corpus to calibrate the reviewer.

11A shared benchmark

ReviewBench gives us another place to start: a shared benchmark for AI code review. It complements a historical review corpus, while our own examples tell us whether the reviewer understands our application.

12Attention is the budget

Every finding costs human attention. Prioritize precision so useful findings do not get drowned out by noise. A reviewer that engineers mute cannot help, no matter how many issues it might otherwise find.

13Earn the right to post

The human stays in charge until the agent demonstrates consistently high-quality results. Start with the agent drafting findings and a person checking them before posting. Hold a high bar for comments that interrupt engineers’ work.

14Measure offline and online

Offline evaluations replay cases where expert review gives us an answer key, using precision and recall. Online evaluations track address rate and fail rate in real work. Engineers acting on findings tells us about actionability, but it does not tell us how many bugs the reviewer missed.

15Different reviewers find different things

No reviewer catches everything. Comparisons of multiple reviewers show that they often flag different locations. That is a reason to combine perspectives, rather than a promise that their combined findings cover every real defect.

16Build a circle of trust

Use reviewers with clear specializations: money movement, security, correctness, and validation. They ask different questions about the same change. A mix of specializations and models can give us more useful perspectives than one general reviewer alone.

17Match review to risk

Dispatch reviewers based on the risk of the change. Routine work gets a smaller review, while money movement or a security boundary brings in specialists and a different policy for human attention.

18Challenge findings before escalating

Reviewers report to an adversarial coordinator agent that challenges claims and consolidates overlap. An adversarial judge then tries to disprove each candidate and checks the evidence. This proposed architecture uses more perspectives to improve coverage and more scrutiny to improve precision, with humans brought in according to risk.

19Reserve human attention

Reserve human review for the most sensitive changes: infrastructure, judgment-sensitive behavior, money movement, SOX-compliant code, and personally identifying information. These signals should reflect the application. An agent’s silence does not remove the need for human judgment.

20What is my job now?

If agents write code and help review it, what is the software engineer’s job? The responsibility shifts toward understanding the experience, setting boundaries, and deciding where human judgment is still essential.

21Contain and align

Contain agents’ impact by choosing the risks we guard against, the boundaries they operate within, and the changes that need extra attention. Align their work with the intent of the application so the factory delivers the experience we actually want.

22Give agents the big picture

AGENTS.md, skills, and tools carry context to our agents. Humans maintain the intended behavior, constraints, application understanding, and knowledge behind those mechanisms. Reviewers need that bigger picture to understand what a change is trying to accomplish.

23Review before implementation

Work in the open and invite teammates into agent sessions. In Buzz, humans and agents collaborate continuously on plans and intent. Getting review before code is written moves judgment earlier, while the implementation is still easy to change.

24This is better

Build the context, tune the risk signals, and collaborate on intent before implementation. Agents can do more of the mechanical work while humans keep responsibility for the program and the experience it creates.
